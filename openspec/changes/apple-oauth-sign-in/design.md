# Design

Apple uses the existing OAuth transaction, exact callback URI, one-time state, nonce, PKCE, provider-subject table, session issuer, and client OS credential bridge. The Apple provider boundary verifies the identity token's signature using the current Apple signing keys (refreshing on an unknown key ID), issuer, configured audience, expiry, and transaction nonce. Its client-secret JWT is generated only inside the provisioned adapter from E1-10 configuration; no credential or live implementation is committed. Deterministic fixtures exercise claim validation and key rotation offline.

Apple's stable subject is the only returning-account lookup key. On first authorization Apple may provide a verified email (including an Apple private-relay address) and a separately supplied name. The provider boundary returns the name only when Apple includes it. The API requires a verified, normalized email only when creating a new binding; it stores the name if supplied and otherwise uses the existing neutral display-name default. For an existing subject, email and name are optional; stored identity/profile data remains unchanged when those fields are omitted. Email collisions still require explicit linking and never merge accounts based on email.

Client UX, callback/cancellation recovery, secure credential storage, and analytics use the Google implementation's approved contract and responsive Welcome states. The Apple button adds no private properties to analytics. There are no new tables, so the existing nightly dump and deletion cascade cover Apple bindings.
