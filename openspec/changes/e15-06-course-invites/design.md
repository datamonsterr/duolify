## API contract
All routes need a session. Errors: `{"error":{"code":...}}`.
- `POST /v1/courses/{id}/invites` body `{"username":"x"}` (method `username`) or `{"friendship_id":"uuid"}` (method `friend`), optional `operation_key` uuid for replay. 201 `{id,status:"pending",expires_at}`. Errors: `course_not_found` 404 (not owner / unknown), `course_not_shared` 409 (private or unpublished: client asks to set visibility `link`), `invite_unavailable` 404 (unknown, self, hidden username), `invite_rate_limited` 429 (+`Retry-After`), `invite_duplicate` 409 (sender already has a pending invite for this recipient and Course).
- `GET /v1/courses/{id}/invites` (owner): `{invites:[{id,status,method,created_at,expires_at,recipient:{username,display_name,avatar}}]}`, newest first, max 100, blocked pairs omitted.
- `GET /v1/invites/received`: `{invites:[{id,created_at,expires_at,read,course:{title},sender:{username,display_name,avatar}}],unread}` pending, delivered, unexpired, sender not blocked either way, course still shared; max 50.
- `POST /v1/invites/read` marks the actor's delivered invites read. 204.
- `POST /v1/invites/{id}/accept` (recipient) 200 `{status:"accepted",course_id:<copy>}`; `decline` and `revoke` (sender) 200 `{status}`. Repeating the same transition is a replay; any other state, owner mismatch or unknown id is `invite_unavailable` 404.
## Decisions
- **Authorization.** Send locks both learners (`social` lock order: ids sorted, `FOR UPDATE`), calls `social.CanInvite(tx,...)`, then writes. Accept locks the pair and the invite row, marks it accepted and commits, then runs `enrollCourse` outside that lock (taking a learner `FOR UPDATE` while enrolling would deadlock on the `courses` foreign key). An accepted invite without `copy_course_id` is retried by a repeated accept, so enrollment happens once.
- **Suppression.** A refused-by-policy invite is stored with `delivered=false`, counts toward the daily cap and shows as pending to the sender, but is never listed to or delivered to the recipient. A second sender inviting the same recipient to the same Course while a delivered invite is pending is stored suppressed the same way.
- **Blocks.** `OnBlock` marks pending invites between the pair `revoked` in both directions in the block transaction; sender lists omit rows whose pair is blocked.
- **Expiry.** Lazy: reads and writes treat `expires_at <= now()` as expired and a sweep in `Maintain` persists it. 30 days (`SHARING_INVITE_EXPIRY_DAYS`).
- **Outbox.** `course_invite_deliveries(invite_id, channel in_app|push, status pending|sent|suppressed|failed, attempts)`, unique `(invite_id, channel)`. In-app is written `sent` with the invite. Push is `pending` only when the recipient allows (`course_invite_push`, default true). The drainer re-checks pending invite, blocks and settings, calls `PushSender`, retries up to `SHARING_PUSH_MAX_ATTEMPTS`, then `failed`. A disabled or failing adapter never affects the in-app inbox.
- **Push adapter.** `PushSender.Send(ctx, PushMessage{RecipientID, InviteID, Kind})`; payload is ids and an enum, so no course material or Username. `DisabledPush` default; `FakePush` records messages for tests and dev (`PUSH_ADAPTER=fake`, refused when `DUOLIFY_ENV=production`). APNs/FCM secrets come only from env vars documented in `.env.example`; no live transport is built until E15-12.
- **Retention.** Final invites purge 90 days after `resolved_at` (`SHARING_INVITE_PURGE_DAYS`, config); in-app inbox rows are the invites, so the list is bounded to 50 and purged with them.
- **Analytics.** `course_invite_sent(method, course_id, invite_id)`, `course_invite_accepted/declined(course_id, invite_id)`, enrollment event carries `source:"invite"`. UUIDs and enums only; no Usernames.
